# slow 시나리오 성능 장애 조사 (2026-10-19)

## 1. 결론

**근본 원인:** 처리 용량(약 **2.2 req/s**, sync 워커 2개) **<** 도착률(**5 req/s**, 개방형 loadgen)으로 accept·ESTABLISHED **대기열이 계속 증가**하고, **대기 시간이 클라이언트 타임아웃(15초)을 넘은 뒤**에는 서버가 처리하는 요청이 **이미 포기된 연결**에 대한 작업이 되어 **goodput(유효 처리량)이 붕괴**한다. 클라이언트가 본 “200 정지”는 서버 정지가 아니라 **SLA 15초 밖에서의 성공 집계 중단**이다.

**확신도: 높음**

- **서버는 정지하지 않았다.** 부록 **표 B**: loadgen 송신 60초 동안 서버 access log **140건** 지속; T+40–50s에도 클라 Δ200=0인데 서버 **34건** 처리.
- 부록 **추정 C**: 분석 창 기준 서버 200 **271건** 중 loadgen 성공 **73건** → 서버 200의 약 **73%**는 **낭비된 작업**(클라이언트는 timeout, 서버는 늦게 200 기록).
- 실험 2(**timeout 60**)는 **해결책이 아니라** “큐+timeout이 goodput을 가른다”는 **메커니즘 증명** (최종 p95 **≈51s** — 그 자체로 장애 수준).
- **관찰:** 부하 종료 후 Recv-Q·백로그를 비우며 `/healthz`가 즉시 200을 돌아오기까지 **약 1분** 회복 지연.

## 2. 증거

### 실험 1 — 재현 + T+10/25/35/45 관측 (`timeout=15` 기본)

| 시점 | Recv-Q | established | close-wait | 워커 wchan | py-spy 요약 | 마지막 앱 로그 (UTC) | loadgen 누계 (200 / timeout) |
|------|--------|-------------|------------|------------|-------------|------------------------|------------------------------|
| T+10s | 22 | 25 | 0 | hrtimer_nanosleep ×2 | (미실행) | 06:46:40.748 | ~20 / 0 |
| T+25s | 70 | 72 | 0 | hrtimer_nanosleep ×2 | (미실행) | 06:46:55.883 | ~39 / 0 |
| T+35s | 74 | 75 | 2 | hrtimer_nanosleep ×2 | **둘 다 `slow()` sleep** | 06:47:05.269 | ~69 / 15 |
| T+45s | 100 | 74 | 28 | hrtimer_nanosleep ×2 | **둘 다 `slow()` sleep** | 06:47:17.244 | ~73 / 52 |
| **[final]** | — | — | — | — | — | (부하 종료 후에도 백로그 처리 지속) | **73 / 226** (sent=299, p50/p95≈15s) |

loadgen 10초 보고: 20 → 39 → 69 → **73(정체)** → 73, timeout 급증. (동일 구간 서버 처리량은 부록 **표 A·B** 참고.)

**회복:** loadgen 종료 후 Recv-Q·백로그 소진 및 `/healthz` 즉시 응답까지 **약 1분** 소요(자연 회복).

### 실험 2 — 클라이언트 timeout 의존성 (`--timeout 60`, 메커니즘 검증)

| 시점 | Recv-Q | close-wait | loadgen 200 누계 | 비고 |
|------|--------|------------|------------------|------|
| T+30s | 73 | 0 | 69 | 로그·처리 지속 |
| T+45s | 96 | 0 | 109 | |
| T+60s | 118 | 0 | 141 | 워커 py-spy: 둘 다 `slow()` |
| T+75s | 86 | 0 | 177 | |
| **[final]** | — | — | **200=299, timeout=0** | p50≈22s, p95≈51s |

**해석 (대조·증명):** timeout 15 → goodput 붕괴(200 ≈73에서 정체); timeout 60 → **집계상** 200=299/299이나 **p50≈22s, p95≈51s**로 tail latency는 여전히 장애 수준. timeout 연장은 **운영 해결책이 아니라**, “대기열+클라 SLA가 goodput을 결정한다”는 **실험 2 증명**에 해당.

## 3. 가설별 판정

| 가설 | 판정 | 근거 |
|------|------|------|
| **H1** 클라이언트가 먼저 끊어 accept 후 read/write에서 막혀 앱 미도달 | **기각** | py-spy T+35/45: 워커 **앱 코드(`slow()`) 내부**; “정지” 구간에도 서버 access log **지속**(부록 표 B). **close-wait**(T+45=28)는 클라이언트가 timeout으로 떠난 뒤 **대기열·백로그에 남은 연결의 결과**이지 1차 원인 아님 |
| **H2** DB 연결/쿼리 블록 | **기각** | `pg_stat_activity`: active 1, idle 다수; py-spy에 psycopg 스택 없음 |
| **H3** 로그 쓰기 블록 | **기각** | py-spy에 `write_log`/`log_file.write` 없음 |
| **H4** gunicorn sync accept 버그 | **기각** | sync 워커는 **한 요청 처리 중 accept 불가** — 설계상 병목(용량 2.2 req/s). 마스터·워커 PID 불변, WORKER TIMEOUT 없음 |

**py-spy가 `slow()`만 보인 이유:** slow-rate 0.3·delay 3s이면 워커 wall time의 대부분이 `/slow` sleep; 10초 슬라이스에서 `/slow` **36/140 ≈ 26%** 건수지만 처리 **시간** 점유는 **≈98%** 수준이라, 무작위 dump가 `slow()`를 잡는 것은 **자연스러운 결과**이지 “전 구간이 sleep에만 갇혔다”는 뜻이 아님.

## 4. 메커니즘

### 쉬운 설명

식당에 **직원 2명(워커)**만 있는데 **초당 5명**이 문을 두드리며(개방형 부하) 안으로 들어와 대기한다. 일부 주문은 **3초(slow)** 걸린다. 손님은 **15초**만 기다리면 포기한다(클라 timeout). 대기열이 길어지면 **15초 안에 차례가 오지 않은** 사람은 전부 포기하고, 손님 통계상 “밥을 받은 사람(200)” 수가 **멈춘 것처럼** 보인다. 주방은 **멈추지 않고** 계속 요리·기록한다(부록 표 B). 실험 2에서 “**60초까지 기다려 주세요**”라고 바꾸면( timeout 60 ) **집계상**은 거의 다 받은 것처럼 보이지만, 실제로는 **50초 넘게** 기다린 사람도 많다(p95 ≈51s) — **식당이 정상이라는 뜻이 아니라**, “기다림 규칙을 늘리면 숫자만 달라진다”는 **실험**이다.

### 기술 설명

- loadgen은 **개방형**: `Thread.start()` 후 `sleep(1/rps)`만 하므로 in-flight 연결 수 ≈ min(rps×duration, rps×(timeout+α))까지 증가.
- gunicorn **sync** 워커는 `accept → handle_request → accept` 루프에서 **handle 중 새 accept 불가**. 용량 ≈ `workers / avg_latency` ≈ 2 / 0.92s ≈ 2.2 req/s ≪ 5 req/s.
- 초과 연결은 리슨 **backlog(Recv-Q)** 및 **ESTABLISHED** 상태로 적재. 워커가 accept할 때까지 스레드는 `urlopen`에서 대기.
- 대기+처리 > **15s**이면 urllib timeout → **goodput 붕괴**(클라 200 정체). 서버는 accept·처리·access log **계속**(부록 표 B). **close-wait**는 포기한 클라이언트 쪽 TCP 잔재.
- 부하 중단 후에도 백로그 처리로 Recv-Q·in-flight가 줄어들기까지 **약 1분** — 용량 < 도착률로 쌓인 연결·작업의 **잔여량**.

## 5. 해결책·프로젝트 방향

**현재 compose(gunicorn sync, 워커 2)는 의도적으로 유지**한다. 본 시나리오는 **재현 가능한 포화·goodput 붕괴** 장애로, **Watcher(Phase 1)** 가 탐지·알림을 검증하는 **대상 부하**로 사용한다.

| 방안 | 역할 | 비고 |
|------|------|------|
| **워커 2 + sync 유지** | 장애 재현·R1~R4 검증 | 용량 2.2 req/s < 5 rps **by design** |
| **gthread/gevent 등 (Phase 3)** | 개선 **전후 비교 시연** | 동일 loadgen으로 goodput·Recv-Q·SLI 변화 측정 |
| **loadgen timeout 연장** | **메커니즘 실험용**(실험 2) | 운영/해결책 아님 (p95 51s) |
| **closed-loop·max concurrency** | 벤치마크 왜곡 제거 | Watcher와 별 트랙 |
| **nginx limit_conn / 큐 (Phase 3+)** | 과적재·503 | 앞단 도입 시 **요청 대기 시간** 헤더 관측 검토 |

## 6. Watcher 설계 시사점

- **앱 JSON 로그만으로는 goodput 붕괴를 탐지하기 어렵다.** 서버 log rate는 유지되는데 **유효 성공**만 사라지는 패턴(부록: 클라 200=73 vs 서버 200=140+).
- **규칙별 기대:**
  - **R1 (앱 로그 기반, 에러율):** 본 장애 **미탐** — access log의 `status`가 **전부 200**(500 **0건**)이라 Watcher가 계산하는 **에러율 0%**로 유지됨.
  - **R2 (latency 임계):** `/slow` **3s sleep** 때문에 p95가 우연히 임계를 넘을 수 있으나, **goodput·큐**와 인과가 분리됨 → 단독 신뢰 낮음.
  - **R3 (처리량 급감):** Watcher가 읽는 **앱 JSON 로그**에서 집계한 **서버 처리 건수(분당·구간당 요청 수)**가 직전 기준 대비 **급감** (클라이언트·loadgen 지표 아님). 본 장애에서는 평소 약 **5 req/s** → 포화 구간 약 **2.3 req/s**(약 **54% 감소**)로 **R3 탐지 가능**.
  - **R4 (합성 프로브):** Watcher가 **`/healthz`를 직접 호출**, **timeout 2s** — 큐잉·포화 시 **즉시 실패/지연** (사용자 `/healthz`와 동일 경로).
- **추가 신호:** 리슨 **Recv-Q**, **established/close-wait** (`ss`), 부하 종료 후 **~1분 회복** 지연.
- **Phase 3+ (nginx 등):** `X-Request-Start` / upstream timing으로 **요청 대기 시간** 직접 측정 검토.

## 부록: loadgen 변경

`scripts/loadgen/loadgen.py` (실험 2 이후·현재 코드 기준):

| 항목 | 내용 |
|------|------|
| **`--timeout`** | 기본 **15**(초). `urllib.request.urlopen(..., timeout=args.timeout)`에 사용. |
| **송신 루프** | `time.monotonic()` + **`next_send += interval`** — 예정 시각 기준 전송. 처리 지연이 있어도 **누적 밀림(drift) 방지**. |
| **스레드 join** | 송신 종료 후 **`deadline = monotonic() + timeout + 5`** 한 번만 잡고, 각 스레드 `join(timeout=max(0, deadline - monotonic()))` — **전체 마감 시각** 기준. |
| **`[final]` 출력** | `sent=`(시작한 스레드 수), **`done=`**(`stats` 합), **`unfinished=`**(sent−done), status dict, `client_p50`/`client_p95`. |
| **인자 검증** | `--rps <= 0` 거부; **`--error-rate + --slow-rate` ∉ [0,1]** 이면 `p.error`. |

- **데이터:** 컨테이너 `/var/log/app/app.jsonl` (읽기 전용 `docker compose exec`).
- **서버 시각:** 로그 필드 `ts` (요청 **완료** 시각, `after_request` 기준).
- **달력 구간:** 06:46:30 ≤ `ts` < 06:48:30, **10초** 단위 (`[HH:MM:SS, HH:MM:SS+10)`).

**읽는 법:** T+30–40s부터 **클라 Δ200=4**인데 **서버=31** → 해당 10초에 서버는 계속 처리·기록하지만, 클라이언트는 15s timeout으로 **성공 집계가 거의 멈춤**. T+40–50s는 **클라 Δ200=0**, **서버=34**.

### “서버는 처리했지만 클라이언트는 이미 timeout” 추정

전제: loadgen 스레드는 timeout 시 **200으로 재집계하지 않음**; 서버는 응답 완료 시 **200 access log**를 남김.

| 추정 | 계산 | 건수 | 설명 |
|------|------|------|------|
| **A (송신 60s, 권장)** | (송신 구간 서버 status=200) − (loadgen 최종 200) = 140 − 73 | **≈67** | 부하 주입 중 서버가 200으로 기록했으나 클라이언트 최종 성공(73)에 포함되지 않은 **하한에 가까운 대표값** |
| **B (10s 슬라이스)** | Σ max(0, 서버 처리 − 클라 Δ200) over T+00…60 | **74** | 구간 경계(완료 시각 vs urlopen 반환 시각) 때문에 표 A보다 소폭 큼 |
| **C (분석 창 전체)** | (구간 내 서버 200, healthz 제외 271) − (클라 200 73) | **≈198** | 송신 종료 **후** 백로그(06:47:31–)까지 포함; “이미 timeout 난 연결에 대한 **늦은** 서버 200” |

**정리:** 실험 1에서 loadgen이 **200으로 인정한 73건**과 달리, **송신 60초 동안만 보면 약 67건**, loadgen **299건 전체**와 서버 access log를 맞추면 **최대 약 198건**까지 서버-side 200이 클라이언트 성공 집계와 **어긋날** 수 있음. **06:48:30 이후** 구간에 **32건**이 추가 기록되어 **분석 창 밖**에서 처리됨. **로그 없이 유실된 요청은 없음**.
