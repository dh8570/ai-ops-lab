## 한눈에 보기

**한 줄 평:** 장애 알림에 LLM 분석을 "실패해도 기본 알림이 가는" 구조로 붙였고, 채점표로 프롬프트 후보를 비교해 어떤 정보를 넣어야 하는지에 첫 답을 얻었다.
다만 운영 기본값(v1)은 사람 채점에서 약했고, 더 나은 후보(v2)는 결함 때문에 승격하지 못했으며, 일정을 11/17에 재조정했다.

## 무엇이 일어났나

**탐험 사이트와 현미경 엔진 (10-28 ~ 10-30, PR #9, #12).** 탐험 사이트 척추(실행 기록 형식, 단계 페이지 틀)를 만들었고, Qwen2.5-7B를 VM CPU에서 직접 계산하는 현미경 엔진(M2-a·b)이 공식 구현과 비트 단위로 일치함을 검증했다. 정밀도 진단에서는 같은 프롬프트의 다음 토큰 확률이 float32 몸통에서 벗어난 정도가 HF sdpa 평균 0.053, Ollama Q4 0.386, 현미경(eager bf16) 0.446이었다(커밋 메시지 기준).

**LLM 알림 (11-2, PR #10, #11, #13, #14).** LLM 호출 모듈(총 30초 상한, 어떤 실패에도 예외 없이 이유 코드로 반환), 근거 집계와 프롬프트 v1, 런북 초안 3개, 알림과 분석을 감시 루프 밖으로 옮기는 dispatcher(FIRING 알림은 즉시, 분석은 후속 메시지, 실패하면 ANALYSIS_FAILED 한 번)를 넣었다. 합격 시험 F(Ollama 없음)·G(LLM 느림)·H(정상)·R4(앱 정지)와 가짜 Ollama 서버도 만들었다. LLM은 기본 꺼짐(LLM_ENABLED 기본 0).

**채점표와 프롬프트 비교 (11-3 ~ 11-5, PR #16, #17, #18).** 시나리오 5개(합성)로 런북 없음 대 있음을 채점하는 도구를 만들고, 사람 채점(정확성·유용성 0~2)과 자동 판정을 대조했다. 이어 프롬프트 v2, 런북을 규칙 번호로 고르는 방식(match), 규칙을 정할 때 보지 않은 보류 시나리오(s8~s11, 그다음 s12~s15)로 후보를 비교했다. 호출 수는 첫 실행 80번, v2 비교 495번, v3 비교 405번이다(커밋 메시지 기준).

**프롬프트 스위치와 그림자 모드 (11-17, PR #19, #20).** 운영 코드에 LLM_PROMPT_VERSION(기본 v1, 기본 동작은 이전과 바이트 같음)과 ANALYSIS_WEBHOOK_URL(AI 분석 알림만 별도 웹훅)을 넣었다. 안전장치로, LLM이 켜져 있고 운영 웹훅이 있는데 분석 웹훅이 없으면 LLM_ANALYSIS_ON_MAIN=1을 명시하지 않는 한 시작을 거부한다. 합격 시험은 분석 채널이 별도이면 시작하지 않는다.

## 잘된 것

1. **"알림 먼저, 분석 뒤따름" 구조.** AI가 느리거나 죽어도 기본 알림은 막히지 않는다. 합격 시험이 이 약속을 자동으로 확인하도록 설계됐다(시험 F·G).
2. **채점표를 먼저 만들고 후보를 비교한 순서.** 느낌이 아니라 같은 시나리오·같은 옵션 7개(temperature 0, seed 42 등)·같은 모델 버전에서 조건만 바꿔 비교했다. 실행 조건이 점수판 맨 위에 박혀 있어 재현할 수 있다.
3. **보류 시나리오를 결과를 본 뒤에도 바꾸지 않은 것.** 규칙을 만든 데이터로만 검증하면 자기 확인이 된다. 새 시나리오(s12~s15)가 v3의 약점을 드러냈다.
4. **자동 판정을 사람 판정으로 계속 의심한 것.** s13의 자동 통과가 사람 1/1이라는 점, s5·s10의 키워드 결함이 모두 사람 채점에서 발견됐다.
5. **운영을 건드리지 않고 켜는 길.** 기본값은 v1 그대로, 분석은 별도 채널에서 먼저 모으는 그림자 모드, 실수로 운영 채널로 새지 않게 막는 시작 거부 규칙.

## 배운 것

1. **런북은 효과가 있다. 하지만 런북에 없는 상황에서는 해가 된다.** 사람 평균 정확성이 런북 있음 1.4 대 없음 0.6(v1, 10칸)이었다. 반대로 런북에 없는 경로(s6)에서는 런북이 없는 쪽이 더 좋았다(2/2 대 1/1). 런북의 다른 장애 항목(DB 연결)을 옮겨 적는 것이 원인이었다.
2. **규칙 번호로 런북을 골라 넣는 방식은 효과가 없었다.** s8~s11 사람 정확성은 match_v1 1.25로 all_v1 1.25와 같았고, match_v2 1.25는 all_v2 2.0보다 낮았다. 다음 단계(RAG 최소판)는 규칙 번호가 아니라 근거 내용(예외 이름, 경로, 프로브 결과)으로 고르는 방식을 시험한다.
3. **v2는 가장 정확하지만 결함이 있다.** 새 보류 사람 정확성 1.75로 v1(0.75)·v3(1.25)보다 높았다. 그러나 "알 수 없음: 이유" 자리표시를 4칸 중 3칸에 그대로 복사했다. 그래서 승격을 보류했다.
4. **7B는 모르는 것을 모른다고 말하지 못한다.** 원인 칸을 1개로 풀어 줘도(v3) 정직해지지 않고 한 원인을 단정했다(s13). 진짜 기권은 어느 조건에서도 나오지 않았다. 이 한계는 프롬프트로 풀리는 문제가 아닐 수 있다(가설).
5. **자동 판정과 사람 판정은 다르다.** 자동 통과인데 사람은 낮은 칸(s13 all_v2의 "알 수 없음" 면제가 통과율을 부풀림), 자동 탈락인데 사람은 높은 칸(s5·s10)이 모두 나왔다. 자동 판정은 방향 확인용이고 결정은 사람 채점으로 한다.
6. **같은 설정에서도 첫 호출만 다를 수 있다.** 캐시 상태 가설로, warm(먼저 한 번 보낸 뒤)에서는 7/7로 같았고 prod에서는 달랐다. 그래서 비교는 warm 기준으로 한다.
