## 무엇이 일어났나

**2-A. 읽고 판단하기 (10-20).** 앱 로그를 1분마다 읽어 R1~R3로 판단하게 했다. 처음엔 "평소 트래픽 기준선"이 엉터리로 계산되는 문제를 세 번 연속 만났다. 이 단계에서 기준선을 평균에서 **중앙값**으로 바꾸고, 평소 트래픽을 계속 흘려주는 `traffic` 서비스를 추가했다.

**2-B. 상태와 알림 (10-21).** 장애를 "사건 하나"로 묶는 상태 관리(정상 → 장애 → 회복 중 → 해결)와 Slack 알림을 붙였다. 재시작해도 하던 일을 이어가도록 책갈피(체크포인트)를 저장했다. 이 단계의 시험 중에 앱이 하루 만에 3배 느려진 것도 발견했다.

**2-C. 빠르게, 정확하게, 자동으로 (10-21 ~ 10-23).** R4(프로브)로 앱 정지를 30초 안에 알게 했고, 새 원인이 늦게 붙을 때만 UPDATE를 보내게 했다. 판단 규칙을 따로 빼서 단위 테스트 29개로 고정하고, 알림 전체를 자동으로 시험하는 합격 시험 스크립트를 만들었다. 중간에 개발 환경(VS Code·Cursor)이 너무 느려서 접속 방식을 바꿨다. 이 단계 후반부터 **클라우드 세션(PM)과 로컬 Claude Code(실행)로 역할을 나눠** 작업했다.

## 잘된 것

1. **판단 근거를 로그에 같이 남긴 설계.** `baseline_n`(기준선에 든 구간 수), `elapsed_sec`(실제 읽은 시간), `added_rules`(새로 붙은 규칙) 같은 값 덕분에 "왜 알림이 안 왔지?"를 로그만 보고 풀 수 있었다. 기준선 오염도 숫자 두 개(평균 311 → 471)로 바로 잡혔다.
2. **"장애 한 건에 알림 한 건" 원칙이 시험에서 일관되게 지켜졌다.** 여러 규칙이 동시에 켜져도 사람에게는 한 번만 간다.
3. **겪은 버그를 테스트로 고정했다.** 빈 구간의 기준선 오염, 재시작 후 처리량 부풀림, 유예 시간 계산 같은 실제 사고가 테스트 이름으로 남았다. 다시 생기면 몇 초 안에 걸린다.
4. **크로스체크 구조가 실제로 일했다.** 로컬 Claude Code가 "이 변경은 의미가 같다"를 근거 세 가지로 증명했고, 자기 보고의 틀린 수치를 스스로 정정했고, "시험이 통과했지만 확인하려던 경로를 지나지 않았다"고 직접 알렸다.
5. **시험을 먼저 실패시켜 보는 습관.** 새 판정(D, E)을 실제로 돌리기 전에 가짜 결과로 "불합격을 낼 수 있는지"부터 확인했다.

## 아쉬운 것

1. **설계의 빈틈이 실험에서야 드러났다.** 기준선에 빈 구간이 들어가는 것, 기준 0.5가 경계에 걸리는 것, 유예를 "창 개수"로 세는 것이 모두 설계 단계에서 한 번만 "이 숫자가 극단적인 상황에서는 어떻게 되지?"를 물었으면 미리 걸렸을 문제다.
2. **개발 환경 문제로 반나절 이상을 썼다.** VS Code가 느린 원인을 찾으면서 두 번 틀렸다(이름 해석 실패를 SSH 문제로 오해, 명령 실행 속도만 재고 "SSH는 빠르다"고 결론). 실제 원인은 접속 방식(Tailscale SSH)이 VS Code의 포트 전달을 못 버티는 것이었다.
3. **설명이 이해보다 앞서갔다.** 위상, 경로, 합성 입력 같은 용어를 풀지 않고 쌓았다. 사용자가 "하나도 이해가 안 간다"고 말해 준 뒤에야 멈추고 처음부터 다시 풀었다.
4. **PM 쪽 실수가 여러 번 있었다** (아래 별도 정리).
5. **시험 때마다 실제 Slack에 알림이 간다.** 의도한 선택이지만, 시험이 쌓이면 진짜 알림이 묻힌다.

## 배운 것

1. **시험의 "통과"는 의미를 따로 확인해야 한다.** 연기를 피우지 않고 "경보가 안 울렸으니 정상"이라고 할 수는 없다. 시험이 확인하려는 상황이 실제로 일어났는지를 판정에 넣는다.
2. **"평소"를 정의하는 값은 가장 먼저 오염을 의심한다.** 기준선, 유예 시간, 임계값 모두 극단적인 입력(0건, 폭증 직후, 재시작 직후)에서 어떻게 변하는지 먼저 따져 본다.
3. **측정은 실제로 쓰는 경로로 한다.** 명령 하나가 빠른 것과, 개발 도구가 쓰는 통로가 안정적인 것은 다르다.
4. **한 장애가 다른 장애를 가린다.** 포화 중에 들어온 에러는 대기열에 묶였다가 풀릴 때 정상 요청에 묻혀 보이지 않았다. 신호 하나만 믿으면 원인을 놓친다.
5. **로그만으로는 부족하고, 로그가 멈추는 장애는 따로 본다.** 앱이 완전히 멈추면 로그가 안 쌓여서 R1·R2는 아무것도 못 본다. 전화를 거는 R4와 "요청이 사라졌다"를 보는 R3가 필요한 이유다.
6. **판단과 실행을 나누면 테스트할 수 있다.** 무한 반복 안에 있던 조건문을 함수로 빼자 몇 초 안에 모든 경우를 검증하게 됐다.

## 3주차로 넘기는 것

### 가장 큰 위험: LLM이 느릴 수 있다

3주차는 장애가 열릴 때 AI가 원인 후보를 요약해서 알림에 붙이는 단계다. 그런데 VM에는 GPU가 없을 가능성이 높아서, 8B급 모델을 CPU로 돌리면 한 번 답하는 데 **수십 초**가 걸릴 수 있다. 그러면 지금 28초 안에 오는 알림이 느려지고, 설계해 둔 30초 시간 제한에도 걸린다. **코드를 쓰기 전에 모델을 실제로 돌려 시간부터 재야 한다.**

### 3주차 시작 전에 정할 결정

1. **"장애 시작" 알림은 AI를 기다리지 않고 즉시 보내고, AI 분석은 뒤따르는 메시지로 보낼 것인가?** 빠른 알림(2분 이내 목표)을 지키려면 이 방향이 안전해 보이지만, 알림이 두 번 가는 것이 "한 장애에 알림 최소화" 원칙과 충돌하는지 따져야 한다.
2. **민감 정보 마스킹을 어디까지 할 것인가.** AI에게 로그를 보내기 전에 IP, 토큰, 이메일을 지운다. 보안이 걸린 부분이라 설계와 구현은 Opus로 한다.
3. 합격 시험의 네 번째 항목("AI가 멈춰도 기본 알림이 간다")을 자동 시험에 추가한다.

### 3주차에 같은 실수를 안 하려면

- 새 숫자(시간 제한, 입력 길이, 모델 크기)를 정할 때 **극단적인 경우**(AI가 응답 없음, 아주 긴 로그, 빈 로그)를 먼저 적어 본다.
- 시험을 만들 때 "이 통과가 무엇을 증명하나?"를 먼저 쓴다.
- 새 용어는 쉬운 말로 먼저, 한 번에 두세 개까지만.
